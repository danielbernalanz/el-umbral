# Política de modelos para subagentes (proyecto El Umbral)

Objetivo: máxima calidad con el mínimo consumo. No tocar el código del juego al aplicar esta política.

1. SONNET (`dev`) es el predeterminado (85-95 % del trabajo): funcionalidades, interfaz, lógica del juego, depuración habitual, refactorización, revisión, análisis, coordinación y planificación. Al lanzar un subagente de programación con la herramienta Agent, usar `subagent_type: "dev"` o `model: "sonnet"`.
2. HAIKU (`mecanico`) para tareas simples, repetitivas y bien definidas: búsquedas, lectura/clasificación de archivos, extracción de datos, ejecutar simulaciones/tests y resumir resultados, comprobaciones mecánicas, revisiones simples. Nunca para funcionalidades complejas ni decisiones de arquitectura.
3. OPUS (`arquitecto`) sólo en casos excepcionales: arquitectura muy compleja, bugs extremadamente difíciles, concurrencia/sincronización multijugador, refactorizaciones de gran envergadura, o cuando Sonnet falló tras DOS intentos razonables. El tamaño de una tarea NO justifica Opus. No usar el modelo Fable en subagentes.
4. Todos los subagentes siguen estas reglas, no sólo la sesión principal: asignar el modelo más barato que haga bien la tarea; no lanzar varios agentes potentes para trabajo equivalente; dividir las tareas complejas en subtareas y repartirlas por modelo.
5. Calidad primero: el ahorro nunca sacrifica calidad de código, seguridad, estabilidad, arquitectura, rendimiento, experiencia de usuario ni fiabilidad del multijugador.
6b. REPARTO CONCRETO PARA AHORRAR TIEMPO (el cuello de botella son las pruebas, no programar): mientras `dev` programa un cambio, lanzar en paralelo `mecanico` (Haiku) para: ejecutar baterías de pruebas/simulaciones y resumir cifras (sim10, smart, smart_human, bh/fuzz.js, tests de UI con navegador), `node --check`, verificar el APK con `unzip -l` (img/, styles.css, fx.js dentro) y que las versiones coinciden en todos los archivos, búsquedas/listados (claves de icono, textos con versión), y revisar capturas con una checklist cerrada. `dev` solo lee el resumen y decide. NO usar Haiku para: corrupción, tentación, equilibrio (decidir qué ajustar), cambios de motor o de interfaz, ni interpretar resultados raros de los bots. Las simulaciones sin cambios de código (línea base) se pueden lanzar con Haiku antes de que termine el cambio, pero deben repetirse tras él.
6. El modelo de un subagente se fija al lanzarlo; para escalar se lanza uno NUEVO (`arquitecto` o `model: "opus"`) con el contexto mínimo necesario.
